# Task 3 Report: Profiles, Skills, and Examples

OpenCode instructions, commands, and a Russian-language quickstart for the wiki's first manual cycle were implemented. The `librarian` and `wiki-maintainer` profiles are primary agents with no model selected. They return JSON only and may read, search, and list project files. All tools are denied by default; write access, shell, network, MCP/custom tools, delegation, external directories, and skill loading are denied. The headless maintenance profile reads `wiki-ingest/SKILL.md` only as a local reference for page format.

Four skills and matching commands were created for ingest, ask, feedback, and maintenance. Commands pass `$ARGUMENTS` in an inert block and instruct the supervising agent to pass Python CLI values as separate argv items or through a JSON file. Arguments are not interpolated into executable shell snippets. The process-page template is in `wiki-ingest/SKILL.md`; its JSON frontmatter object matches the wiki validator.

At the time of this report, the README documented Python 3.11+, the virtual environment, model configuration in `[ask]`, an absolute `--root`, importing synthetic materials, manual proposal processing, completion against a Git commit, feedback, and SQLite backup through the backup API. It recorded the POSIX requirements for macOS/Linux and the absence of a daemon and automatic publication. The examples included a workflow, a procedure, a derived code summary with an intentional conflict, a request JSON file, and a feedback JSON file. At that time, `docs/check-questions.md` contained five manual checks: a direct fact, synthesis, a conflict, an unknown answer, and a repeat after publication review.

The profile's answer contract was aligned with Task 1: the model returns `scope`, `summary`, `claims` (`claim_id`, `text`, `status`, `citation_ids`), `citations` (`citation_id`, `source_id`, `revision`, `locator`, nullable `wiki_page`), `gaps`, and `conflicts`. Python adds `question`, `answer_id`, and `wiki_revision`, a SHA-256 digest of the current wiki and registered sources. This differs from the Git commit SHA used to complete a proposal. Locators are limited to `line:<n>`, `line:<n>-<m>`, and `section:<slug>`. The proposal contract was aligned with Task 2; `evidence` includes an exact source, revision, and locator, and `wiki_page` may be `null`.

Syntax was checked against the official OpenCode documentation: [agents](https://opencode.ai/docs/agents/), [skills](https://opencode.ai/docs/skills/), [commands](https://opencode.ai/docs/commands/), and [CLI](https://opencode.ai/docs/cli/). The implementation uses Markdown profiles with `mode: primary` and explicit permissions, the required `name`/`description` skill frontmatter fields, and `$ARGUMENTS` only as prompt data. It does not use the executable shell placeholder `!`. The documentation was read on 2026-10-04; OpenCode 1.18.18 remains the project's baseline.

No separate live model call was run. At the parent's additional request, `tests/test_workflow.py` was added as a CLI integration cycle using fake OpenCode, SQLite, Git, and an external cwd. The focused run through bundled CPython and Node passed: 1 test in 1.26 seconds. It confirmed safe invocation from another directory, idempotent source registration and feedback, saving a proposal without changing the wiki, exact content verification in the Git commit, and a new `wiki_revision` digest after publication. The parent performs the full repository integration check.
